# Run-3 Levers Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the three bottlenecks run 2 exposed by direct diagnosis, so a produced finding actually reaches a gated done-session, then re-measure. Evidence (run 2, doc-reader-with-t1): the critic produced a **verified high-severity** path-traversal finding — but it landed 9s **after** the 45s gate gave up (`delivered: null`), and the medium finding that landed in-window still wasn't delivered because a finished one-shot has no future PostToolUse to inject it.

**Architecture:** Three levers, each independently correct and testable. (1) The gate must stay held while the critic is genuinely mid-judgment on the final change, not release on a fixed cap that's shorter than judge+verify latency. (2) At a **gated** Stop specifically, medium+ findings must be deliverable (block once), because there is no later injection point. (3) The harness must run the high-recall prober (only 2 findings in 15 sessions with the precision-anchored default alone). Pure decisions stay in `hooks/logic.py`; the wait stays in `hooks/peer_hook.py`; harness changes in `evals/ab/run.py`.

**Tech Stack:** stdlib only; seams `hooks/logic.py`, `hooks/peer_hook.py`, `evals/ab/run.py`, `critic/main.py` (prober passthrough already exists).

### Task 1: Gated-mode delivery — medium+ blocks once at a gated Stop

The finished-one-shot problem: at Stop, only high blocks; medium delivers via the next PostToolUse, which never comes. When the gate is active (this Stop is being held for the critic), a medium-or-high finding for this session must block once so it reaches the agent.

**Files:**
- Modify: `hooks/logic.py` (pure — `decide()` gains a `gated: bool` param; when True, medium+ suggestions block at Stop like high does today, still once-each, still never on `stop_hook_active`), `hooks/peer_hook.py` (pass `gated=True` into `decide()` only when a gate wait was actually performed this Stop)
- Test: `tests/test_hooks.py`

**Interfaces:**
- `decide(..., gated: bool = False)` — default False = today's behavior byte-identical. gated=True: the Stop-block severity floor drops from high-only to medium+. High still blocks whether or not gated. Ledger once-each unchanged.
- peer_hook: `_maybe_wait_for_critic` already knows if it waited (it marked the gate ledger key); thread a `gated` boolean out of it (True iff a wait happened / gate active this Stop) into the `decide()` call.

- [ ] **Step 1: Failing tests** — gated=False: medium at Stop does NOT block (unchanged); gated=True: medium blocks once, second identical Stop does not re-block; gated=True still respects `stop_hook_active` (no block); high blocks in both modes.
- [ ] **Step 2: Implement** the severity-floor branch in decide() + the gated flag threading.
- [ ] **Step 3: Suite green; README; ruff; commit.**

### Task 2: Gate waits for the in-flight judgment, and harness run-3 config

The gate released on its cap while the critic was still verifying. Two parts: make the gate's default cap adequate for judge+verify, and give the harness the run-3 knobs (prober on, longer gate).

**Files:**

- Test: `tests/test_ab.py`

**Interfaces:**

- without/naive arms: no prober, no gate (unchanged).
